# Configuring AD FS

AD FS in one of the available services that can act as an IdP enabling SPs to communicate with it using the SAML 2.0 standard. This service is responsible to provide Single Sign-On (SSO) of existing users as well as to enable user provisioning. For certain actions, the AD FS can be configured in different ways. Full description of the AD FS configuration is beyond the scope of this guide, however, basic configurations that enable SSO in Pulse are described below as examples. These examples include:

  * Obtaining Pulse IdP properties when using AD FS.
  * Configuring Pulse in AD FS as a Relying Party Trust (i.e. SP).
  * Configuring users in AD FS that are mapped to Pulse users.
  * Configuring claim rules in AD FS that will be part of the SAML assertion to communicate user information to Pulse such as language, groups, roles, or tenants.



## Obtaining Pulse IdP propertiesâ

When the IdP used is the AD FS, all the Pulse's IdP related properties (prefix: `pulse.manager.services.core.security.authplugin.filter.samlsso.idp`) can be obtained from the AD FS federation metadata file. This federation metadata is available using the following URL:

`https://<ADFS_DOMAIN>/FederationMetadata/2007-06/FederationMetadata.xml`

The federation metadata file contains various information about the AD FS instance. To know how to map the information contained on this XML to the Pulse properties, please check: [Configuring SSO using a generic IdP](/pulse/latest/docs/common/pulse/administrators-guide/securing-an-environment/single-sign-on/configuring-sso-using-a).

## Add a relying party trustâ

This section describes how to configure a Pulse instance as a relying party trust (i.e. SP).

The SP can be configured manually or automatically by importing configuration data generated by metadata. The second method is described in this section as an example.

At this point you should have AD FS installed, and the properties that enable SSO configured on Pulse.

AD FS configurations

Note that the SP configuration based on importing configuration data from metadata described in this section is not necessary the preferred method for all the production systems. This method is illustrated in this section as an example. Refer to the [AD FS Documentation](https://docs.microsoft.com/en-us/windows-server/identity/ad-fs/operations/create-a-relying-party-trust) for full configuration details.

  1. Open the Pulse URL that provides metadata information for the specific instance, e.g. `https://<BASE_PULSE_ADDRESS>/pulseviews/api/sessions/samlsso/metadata`, and export the file as XML.

  2. Open the **Server Manager AD FS**.

  3. In the Server Manager AD FS, open the **Tools** bar and select the option **AD FS Management**.

  4. In the AD FS window, expand the folder **Trust Relationships**.

  5. Open the folder **Relying Party Trusts**.

  6. In the **Actions** panel, choose the option **Add Relying Party Trust...**.

  7. Click start, and choose the option **Import data about the relying party from a file**.

  8. Open the XML file generated in Step 1 and click **Next** to create the SP. Note that at the end of this step you can open the IdP sign in webpage and check that the new SP is already available.

## Create claim rulesâ

This section describes how to configure claim rules to map Pulse user name and two user roles. The AD FS claims rules are sent as attributes within SAML assertions. They are essential for Pulse to perform user provisioning correctly.

The configuration of the AD FS to map user roles is optional along with languages, groups, and tenants. Therefore, the configuration described in this section is only an example of a configuration option.

  1. Open the **Server Manager AD FS**.

  2. Open the **Tools** bar and select the option **AD FS Management**.

  3. In the AD FS window, expand the folder **Trust Relationships**.

  4. Open the folder **Relying Party Trusts**.

  5. Choose an item from the list of relying party trusts that you wish to establish the claims, right click on the item and select **Edit Claim Rules...**.

  6. Select **Add Rule** , and select the claim rule template _Send LDAP Attributes as Claims_.

  7. Provide the following information:

     1. Claim rule name: _Name ID._
     2. Attribute store: _Active Directory._
     3. LDAP Attribute: _User-Principal-Name._
     4. Outgoing Claim Type: _E-Mail Address._
  8. Add another rule and select the claim rule template _Transform an Incoming Claim._

  9. Provide the following information:

     1. Claim rule name: _Email claim_.
     2. Incoming claim type: _E-Mail Address_.
     3. Outgoing claim type: _Name ID_.
     4. Outgoing name ID format: _Email_.
     5. Select the option **Pass through all claim values**.
  10. (Optionally) Add another rule and select the claim rule template _Send Group Membership as a Claim_.

AD FS configurations

Note that the choice of the claim rule template described in this section is not necessary the preferred option for all the production systems. This option is illustrated in this section as an example. Another option is to extract the claims from the LDAP attributes. Refer to the [AD FS Documentation](https://docs.microsoft.com/en-us/windows-server/identity/ad-fs/deployment/configuring-claim-rules) for full details about configuring claim rules.

  11. Provide the following optional information:

     1. Claim rule name: e.g. _RoleAdminCheck_.
     2. Outgoing claim type: e.g. _User.roles._ Note that this property is used by Pulse by default to map to a user role. For example, the properties User.language, User.groups and User.tenants would map to languages, groups and tenants.
     3. Outgoing claim value: e.g. _admin_. Note that this value maps to a user role in Pulse, and thus, it has to match the name of the role configured in Pulse. For example, to map to a tenant, the claim value has to match the tenant name configured in Pulse.
  12. (Optionally) Repeat Steps 10 and 11 to add a claim rule to map to the Pulse role _pulseviews_.

  13. Repeat Steps 5 to 12 to create claim rules for other SPs.
