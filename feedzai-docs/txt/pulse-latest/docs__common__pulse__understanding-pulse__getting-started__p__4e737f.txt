# Processing Data

Was this page helpful?Â 

Now that you have loaded your data into Pulse, the next step is to transform your data and extract value from it. At this stage you will learn how to design [plans](/pulse/latest/docs/common/pulse/understanding-pulse/core-concepts/plans) so that you can design derived features or extract subsets of your original data set, before training a model.

## Designing derived featuresâ

It is often useful to enrich your dataset with derived features that can be useful to distinguish between the classes you wish your model to predict (in this case, _fraud_ and _not fraud_). Design a plan that calculates a feature as follows:

  1. In the **Data Science** tab, add  a new plan named _Features_.
  2. Set the plan as **Deployable**. Generating derived features is useful both in data science and in production [workflows](/pulse/latest/docs/common/pulse/understanding-pulse/core-concepts/workflows). Enabling this option allows you to take this work directly into the runtime environment without any extra effort.
  3. In the the **Schema** field, set the schema to be copied from the _RawTransactions_ data source (confirm the orange warning sign below) and **Save** it.
  4. Use a **Map** operator to calculate derived features. You can design a feature that represents the distance between the merchant and the customer's home location (since a greater distance has a higher correlation with fraud). ## Designing historical profilesâ

Another kind of features that is also often useful are the ones based on [historical behaviour](/pulse/latest/docs/common/pulse/users-guide/feature-engineering/creating-metrics). To calculate historical profiles (i.e. metrics), such as the daily count and sum of transactions, execute the following actions:

  1. In the _Features_ plan, use the  button to select other options, and select the **Plan Settings** option.

Under **Timestamp Field** , select the field called _Timestamp_. This is required so that Pulse knows which field from the dataset represents when events occurred so that it can build time-based features.

  2. Add a **Metrics** operator and connect it after the _AddDistance_ operator.

  3. Edit  the metrics operator to name it _Metrics_ and check the **Output Incomplete Instances** option.

Initial events will not have accurate metrics. For example, a metric with a window of 24 hours will only be correct after the first 24 hours of the data. Hence these events are called incomplete instances. By default, Pulse discards the initial events with incomplete metrics, to improve model training and evaluation. Select the **Output Incomplete Instances** option if you want to include them anyways.

  4. Add  a new metric, and define it as follows:

     1. In the **Group By** section, select the _AccountID_ field. This means that the metric will be calculated for each account.
     2. In the Window section, leave the default _1 hour_. This means that you want to calculate a metric based on the events of the last hour.
     3. In the **Aggregation** section, select the function _Count_. This means that the metric calculates the number of events in the respective window (last hour).
     4. Use the **Save** button to add the metric to the operator.
  5. Add  another metric following the same steps, but this time the window is _1 day_. This metric calculates the number of events in the last day.

  6. Add  a new metric, and define it as follows:

     1. In the **Group By** section, select the _AccountID_ field.
     2. In the **Window** section, leave the default _1 hour._
     3. In the **Aggregation** section, select the function _Sum_ , and the field _TransactionAmount_. This means that the metric calculates the total amount of the events in the respective window (last hour).
     4. Use the **Save** button to save the metrics.
  7. Add  another metric following the same steps, but this time the window is _1 day_. This metric calculates the total amount of the events in the last day.

  8. Use the  button next to the metrics' names to change them to _HourlyTrCount_ , _DailyTrCount_ , _HourlyTrSum_ , and _DailyTrSum_ , respectively.

  9. Use the **Save** button to save the metrics operator. Your feature plan will look like the following image:

  10. Use the  button to run the plan and create a new and enhanced data source including your features. Configure the execution as follows:

     1. In the **Data Source** section, select _RawTransactions_ as the input data source.

     2. In the **Data Sinks** tab, name the data sink as TransactionsFeatures, and leave the file type as the default (Parquet). In the **Directory Path** field, specify the output file URL. Set the path to the Pulse server home directory, ending with `/var/datasources/<filename>`.

Example: `file:///PULSE_SERVER_HOME/var/datasources/transactions-features.parquet`

The file path may vary according to the operating system of the Pulse server. You can not have a file with the same name in the datasources folder.

     3. Use the **Run** button to execute the plan.

  11. **Save** the plan and then press the **refresh** button on browser.

You can see in the **Data Science** tab that you now have a new data source. You can analyze it as you have done before with _RawTransactions_ , and assess the usefulness of the features you have designed.




## Sampling your dataâ

It is often useful, in the context of Data Science, to reduce the size of the dataset while generally maintaining the distributions of the random variables representing each feature. This is done via [stratified sampling](/pulse/latest/docs/common/pulse/users-guide/creating-a-data-science-project/processing-your-data/analyzing-and-sampling-your-data/creating-a-stratified-sample).

Sampling improves the performance of your Data Science Loop since you will be able to iterate much faster on feature calculation and model training.

Create a stratified sample to reduce the number of _Accounts_ where there was no _Fraud_ to be 10% of its original size, as follows:

  1. Add  a new plan named _Stratify_.

Make sure that the **Deployable** checkbox is **not** selected. This means that this plan will be non-deployable. Non-deployable plans are useful for sampling data, which typically happens only in the data science environment, hence the plan won't need to be deployed to production.

You can run this plan as you have done with the _Features_ plan to generate a new data source (do not forget to select the RawTransactions as your base data source). You can then verify, by evaluating it and performing an exploratory data analysis, if this sample really is representative of the original data set. For most data sets, this is true. You will not be using this sample (or any other) during this tutorial since the original data set is fairly small already. This allows you to operate on it without resorting to sampling.

However, it is encouraged that you to use this technique on real projects with substantial data sets.
