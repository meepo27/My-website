# Monitoring Processing of Feedback Records in Pulse

This page describes how to monitor the processing of feedback records in Pulse using the `/metrics` endpoint.

## Introductionâ

Feedback records are a core concept of Pulse that allow users to provide feedback about past decisions from the system, e.g. when a transaction was previously marked as not fraudulent, but was actually fraudulent. This mechanism allows:

  * Data Scientists to re-iterate over the metrics, rules and Machine Learning models used by the workflow, and use the feedback to iteratively improve the performance of the system.
  * Users to evaluate the performance of the system by comparing the decisions of Pulse with the received feedback.



The Feedback Storage Service is the service responsible to manage all the CRUD operations related with feedback records.

It is essential to know if this service is operating within reasonable limits. By taking monitoring metrics from the Feedback Storage Service, Pulse operators can have access to different information related to feedback operations via the `/metrics` endpoint.

## Metricsâ

The metrics are associated with an application, identifiable via an `appSlug` tag, where the service is running.

The `appType` and `metricType` tags, that are also associated with these monitoring metrics, are common to other metrics exposed in Pulse and App Engines. They inform where the metrics were collected (Pulse Server or App Engine) and what type of metric it is being reported (e.g. APPLICATION), respectively.

Gauges  
      
    
    pulse.feedbackstorage.status

|  The current status of the Feedback Storage Service. This state is computed by looking at the current state of the internal components of the service. This means that: 

  * If **all components are UNAVAILABLE** , then the **service is UNAVAILABLE**.
  * If **all components are AVAILABLE** , then the **service is AVAILABLE**.
  * If the **components have different states** then the **service is DEGRADED**.

The DEGRADED state can happen, when for example feedback messages are dropped to the deadletter because of an issue in either the Event Storage or the Messaging Broker.  | # | 0 - UNAVAILABLE

Timers  
Timers contain the following metrics: 

  * **count:** Number of events;
  * **max:** Max Latency;
  * **mean:** Mean Latency;
  * **min:** Minimum Latency;
  * **p50:** Latencies in the percentile 50;
  * **p75:** Latencies in the percentile 75;
  * **p95:** Latencies in the percentile 95;
  * **p98:** Latencies in the percentile 98;
  * **p99:** Latencies in the percentile 99;
  * **p999:** Latencies in the percentile 99.9;
  * **stddev:** Standard deviation of the latencies;
  * **m15_rate:** Rate in the last 15 minutes;
  * **m1_rate:** Rate in the last 1 minute;
  * **m5_rate:** Rate in the last 5 minutes;
  * **mean_rate:** Mean rate;
  * **duration_units:** Seconds;
  * **rate_units:** Calls/Second;
