# Monitoring Processing of Profiles in PKernel

Was this page helpful?Â 

PKernel is used to calculate real-time metrics to enrich events.

Having in mind that the majority of projects create real-time metrics, it is essential to know if PKernel is operating within reasonable limits. By taking monitoring metrics inside PKernel, we let Pulse operators to have access to different information related to PKernel via the /metrics endpoint.

These metrics are associated with:

  * a given PKernel, which is identifiable via a pkernelID tag;
  * a plan workflow element, which is identifiable via the workflowElementID tag;
  * a workflow, identifiable via the workflowID tag;
  * an application, identifiable via an appSlug tag.



Besides using the abovementioned tags to identify the PKernel monitoring metrics in the scope of an application, in certain cases, it is also necessary to identify the metrics in relation to PKernel components where these are being collected. This is possible through the following tags:

  * `queryName` \- Used when metrics are being registered inside a PQL query. The value that is assigned to this tag is the name of the query on the PQL plan code.
  * `stateType` \- Used when the metrics are related to operations performed on a given type of state object. The values associated with this tag can be deque or map. Deques are windows that contain the events processed within a certain time-frame; maps are dictionaries that contain the aggregations (e.g., avg, max) grouped by the values present in certain fields of an event.



The `appType` and `metricType` tags, that are also associated with these monitoring metrics, are common to other metrics exposed in Pulse and App Engines. They inform where the metrics were collected (Pulse Server or App Engine) and what type of metric it is being reported (e.g., APPLICATION, BUSINESS), respectively.
