# Pulse Probes

Was this page helpful?Â 

Pulse probes provide a means to expose Pulse internal instrumentation data, allowing it to be stored in a central location for subsequent analysis.

## Probing Componentsâ

The Pulse probing architecture is composed of two components:

  * **Probes** that periodically measure some relevant metrics (for example, processing latency) and broadcast their values to a **metric server** that may be listening to them. Probing is performed either as a response to a pulse internal event (e.g. a fraud event passing by a fraud rules service workflow element) or on a periodic basis (e.g. get sample of X every Y seconds). Each probe has an associated **metric schema** , that contains the fields that correspond to the metric. Probes are normally tightly coupled to Pulse components.
  * **Metric Server** , that are subscribers of the metric information published by the probes and that store received metric information in CSV files. Metric servers may register/unregister themselves on the existing probes.



Note that the term "metric" in this context refers only to whatever is measured by probes, and should not be confused with PQL metrics.

Metric servers communicate with probes for registering/unregistering themselves and for probe discovery using a topic named `metrics_control_topic`; metric events are broadcast to metric servers through direct TCP connections.

This architecture is extensible, allowing you to create your own probes for any pulse component you develop (e.g., custom workflow services).

## Running a Metrics Serverâ

A metrics server deployment is composed of a single standalone jar file (**metrics-server- <version>.jar**) and a properties file with its configuration, named **metrics.properties** by default. A sample configuration file is included. In order to launch a metric server just run:

`java -jar metrics-server-<version>;.jar [properties_file]`

Metrics servers can run in two modes:

  * **Interactive (REPL enabled)** , where a shell is provided for registering/unregistering the server on probes in an interactive way.
  * **Non-interactive (REPL disabled)** , where the server will only handle auto-started probes (see _metrics.autostartprobes_ below). When used this way, the metric server must be started before the Pulse server (or, more exactly, before the probes that are to be listened for start).



The server run mode is specified in the _metrics.replenabled_ property of the configuration file (see below).

The _properties_file_ argument can be used in case you need multiple configurations on the same host. If not specified, the default _metrics.replenabled_ properties will be used.

## Interactive Commandsâ

The commands available in interactive mode are the following:

  * `l[ist] [pattern1[,pattern2]]` \- shows the available probes and their status. Absence of a pattern means all probes.
  * `r[eport] pattern1[,pattern2]` \- start listening on the probes specified in pattern.
  * `s[ilence] pattern1[,pattern2]` \- stop listening on the probes specified in pattern.



Probe pattern names support the wildcard characters `*` and `?`. The `*` wildcard matches a sequence of zero or more characters and the `?`matches exactly one character.

The list of existing commands can be displayed on the shell just by entering an empty line.

< 15.1.10

Make sure that you silence your patterns before exiting the server! If you report for a given pattern, shutting down the server and leaving interactive mode does not stop the pattern from being reported.

Since 15.1.11 metrics server will silence all probes when sucessfully shutdown.

## Metrics Server Propertiesâ

The `metrics.properties` has the following properties.

Property| Description| Default Value  
---|---|---  
**metrics.autostartprobes**|  The server will register on the probes that match these patterns and that start after the metrics server starts.  
  
Patterns support the wildcard characters `*` and `?`. The `*` wildcard matches a sequence of zero or more characters and the `?` matches exactly one character.|  None  
**metrics.host**|  The host of the metrics server. Probes will report connecting to this host.|  hostname reported by `InetAddress.getLocalHost().getHostName()` or `localhost` if that fails.  
**metrics.port**|  The port the metrics server is listening on. | 16161  
**metrics.replenabled**|  Whether the metrics server should run in interactive mode or not.| true  
**metrics.store.outputdir**|  Metrics will be stored to files in this folder. This folder will be created if does not exist.| Mandatory property.  
**metrics.messaging.***|  Messaging can be configured with the usual messaging configuration properties prefixed by `metrics.messaging.`.  
  
Must match the pulse-side messaging configuration.| Embedded ActiveMQ. Only works when probes and metrics server are on the same machine.

## Storing Metric Data Locallyâ

Probes can also be configured to write metric data directly to a local text file, using the logging framework. This setup doesn't require a metric server but allows only for metric data to be stored locally on (each) Pulse Server and doesn't allow individual probes to be "disabled", as when using the metric server.

The Pulse standard log configuration file (`PULSE_HOME/conf/logger/logger-metrics.xml`) includes a commented out section with an appender (`METRICS-ASYNC`, that in turn uses the `METRICS` appender) and a logger for that appender. In order to have the probes writing directly to files it is enough to uncomment this section.
    
    
    <!--  
        Start of metrics server local logging.  
        By default this logger is disabled. This means that probes will not be logged to disk,  
        only reported to the metrics server if enabled.  
      
        With this logger metrics server doesn't need to be enabled.  
      
        Use an AsyncAppender to avoid impacting the critical path of execution degrading processing latencies.  
    -->  
    <!-- METRICS SERVER LOGGING TAG  
    <appender name="METRICS" class="ch.qos.logback.core.rolling.RollingFileAppender">  
      <file>log/${pulse.logcontext}-metrics.log</file>  
      <encoder>  
        <pattern>%msg</pattern>  
      </encoder>  
      <rollingPolicy class="ch.qos.logback.core.rolling.TimeBasedRollingPolicy">  
        <fileNamePattern>log/${pulse.logcontext}-metrics.%d{yyyy-MM}-week-%d{WW}.log.gz</fileNamePattern>  
        <maxHistory>8</maxHistory>  
      </rollingPolicy>  
    </appender>  
      
    <appender name="METRICS-ASYNC" class="ch.qos.logback.classic.AsyncAppender">  
      <appender-ref ref="METRICS" />  
      <queueSize>2048</queueSize>  
      <discardingThreshold>0</discardingThreshold>  
      <includeCallerData>false</includeCallerData>  
    </appender>  
      
    <logger name="com.feedzai.metrics.probes.TextAbstractProbe" level="TRACE" additivity="false">  
      <appender-ref ref="METRICS-ASYNC" />  
    </logger>  
    METRICS SERVER LOGGING TAG -->  
    <!-- End of metrics server local logging. -->
