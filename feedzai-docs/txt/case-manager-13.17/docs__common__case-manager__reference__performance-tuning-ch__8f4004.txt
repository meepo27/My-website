1| **Plan for removing/detaching old partitions  
**

  * In PostgreSQL, too many partitions may cause severe database performance degradation.
  * Around 100-300 partitions across the whole database seems to work. More than that may result in issues. At 100 partitions for a particular table, performance may start to degrade.
  * Read [Performance issues with PostgreSQL partitioning](/docs/internal/case-manager/configuration-guide/database-performance/performance-issues-with-postgresql)
  * Deleting or detaching old partitions that fall out of the data retention policy helps keep the overall number low.

| 

  * Keeps database healthy
  * Increases overall CM performance

10| **Alerts/Search page configuration must refer the correct timestamp field**

  * Event listing pages that refer to event's timestamp, either in page layout (columns) or page queries (filter), must be configured to refer the event's core `timestamp` field, and not to any other fields that may also holding the events timestamp, such as `schema.fields.timestamp`.
  * Miss-configuring this will prevent CM from be able to take part of database partitioning, as`timestamp` is the schema partitioning field. Check example below:**qui-config.json****Expand source**
        
             {
                 ...
                 "configurationInstance": {
                     "pages": {
                         "alerts": {
                             "type": "listing",
                             "title": "alerts.title",
                             "config": {
                                 "table": {
                                     "filter": "'alert' eqb 'true' AND 'statusId' eq 'unknown'",
                                     "linkTo": "event",
                                     "columns: [{
                                                 "key": "timestamp", // this should be "timestamp" and not "schema.fields.timestamp"
                                                 "type": "timestamp",
                                                 "title": "event.timestamp",
                                                 "cssClass": "fdz-css-align-left fdz-css-text--xsmall fdz-css-lh--large",
                                                 "sortable": true
                                             },
                                     ...
             }
             


| 

  * Reduce page load latency

11| **Fine-tuning parameters in config.json**

  * `config.json` allows to tweak some parameters regarding CM internals, such as:  

    * The number of worker threads to process the events arriving from Pulse.
    * The size of CM's internal buffer to hold the events (pre)fetched from EVENT queue.  

    * The threshold of events to be stored in batch.  

    * The timeout to trigger the storage of events in batch.  

    * The limit threshold of retrieved events from listing queries.  

  * These parameters can be changed via config.json file (CM restart needed):  
**config.json****Expand source**
        
        {
                 ...
                 "performance": {
                     "event_worker_threads": 8,
                     "queue_prefetch_size": 200,
                     "batch_storage_size": 300,
                     "batch_storage_timeout": 1000
                 }
             }

15| **Read-Only Replica Database**

  * Allows to redirect CM's UI event-based requests, such as Alerts, Events, and the Details page's Transaction History to a read-only database (ie. a read-only replica of CM's main database).
  * Rational is to prevent CM's (main) database from being overwhelmed with user activity requests while it is already processing events arriving from Pulse.
  * Docs: [Read-Only Replica Database](/docs/internal/case-manager/configuration-guide/read-only-replica-database)

| 

  * Reduce contention in database by scaling it with a read-only replica

| **Core config file:**

  * `config.json`
  * `gui-config.json`

  
16| **Avoid large table scans on the Case Linked Events widget (Postgres specific)**

  * This widget is typically configured to display the Case Linked Events sorted by event date; however, on large volume deployments, configuring the widget to use only this field may lead to poor query performance. In order to prevent this, please add the eventId field to the sorted fields in gui-config.json, i.e.:

**Expand source**
    
    
         ...
         "orderBy": "timestamp desc, id asc",
         "orderByFallback": [
             "timestamp desc, id asc"
         ],
         ...
         

| 

  * Linked events retrieval reduced from 90 seconds to 54 ms (on a particular deployment).

| **UI config file:**

  * `gui-config.json`

  
17| **Configure the Notifiers feature for Insights**

  * If you use Insights, then data should be sent to it via a message broker, using [Case Manager's external notifications feature](/docs/internal/case-manager/configuration-guide/external-notifications). Then, you can use Insights' CM Logstash pipelines to ingest the data from the message broker. This increases CM's overall throughput significantly.   
This can be configured in config.json, by adding the following:

**Expand source**
    
    
         "notifications": {
             "enabled": true,
             "queue_size": 100000,
             "pool_size": 1,
             "cool_down_period_millis": 1000
         }

Read more about this configuration [here](/docs/internal/case-manager/reference/core-config-json#notifications).| 

  * Increase in event throughput

18| **Configure the batches**

  * Case Manager offers a series of batches used to perform a multitude of tasks, such as:
    * Persisting events to **AM_EVENT_STORAGE** (or all event tables when **ignore_event_updates** is true - see [performance configuration](/docs/internal/case-manager/reference/core-config-json#performance)): **event_storage_batch**
    * Persisting automation rule actions: **automation_actions_batches**
    * Persisting event explanations: **batch_storage_size** and **batch_storage_timeout**
    * Persisting entries to **AM_AUDIT** : **audit_batch**
    * Executing background healthcheck tasks: **healthcheck_worker_threads** and **max_queued_healthchecks**
All of these properties can be configured in the **performance** property of the **config.json** file. For a better performance, ensure you configure these properties according to your requirements.

**Expand source**
    
    
         "performance": {
           "batch_storage_size": 300,
           "batch_storage_timeout": 1000,
           "event_storage_batch": {
             "queue_size": 500,
             "batch_size": 500,
             "batch_timeout": 1000
           },
           "automation_actions_batches": {
             "queue_size": 500,
             "batch_size": 500,
             "batch_timeout": 1000
           },
           "audit_batch": {
             "queue_size": 250,
             "batch_size": 150,
             "batch_timeout": 1000
           "healthcheck_worker_threads": 6
           "max_queued_healthchecks": 12
           }
         },

Read more about this configuration [here](/docs/internal/case-manager/reference/core-config-json#performance).| 

  * Decrease in database load
  * Increase in event throughput

| **Configuration:**

  * `config.json`

  
19| **Configure CM to ignore event updates, if possible.**

  * If your project does not require Case Manager to process event updates, ensure that **ignore_event_updates** is set to **true**
  * This allows CM to make a few, very valuable optimizations:
    * Disable the query made, for each event that arrives, that checks whether that event is an update.
    * Persist events using batches, thus increasing throughput. Note that the configuration for this batch is defined by the [event_storage_batch](/docs/internal/case-manager/reference/core-config-json##eventstoragebatch) property.
This property can be configured in the **performance** property of the **config.json** file:**Expand source**
    
         "performance": {
           ...
           "ignore_event_updates": true,
           ...
         },
         


| 

  * Increase in event throughput

| **Configuration:**

  * `config.json`

  
20| **Consider using the state machine's initial_state property to set the initial state of events, instead of relying on automation rules.**

  * The **initial_state** property of the configuration of state machines allows defining a state that will always be set for new events. The way this is done is heavily optimized and, as such, is significantly cheaper than doing it via automation rules.
  
This property can be configured in the **state_machines** property of the `config.json` file:**Expand source**
    
         "state_machines": [{
           ...
           "key": "status",
           "initial_state": "PULSE",
           ...
         }],
         


| 

  * Increase in event throughput
  * Reduction of database load

  * `config.json`

24| **Delay event reads**

  * Ensure that, if the event storage listing is active, the event retrieval should not include the immediately stored events (in **AM_EVENT**) but should be delayed as the **AM_EVENT_STORAGE** may have not been written.
  
This property can be configured in the **listing** property under **event_properties** of the **config.json** file:

    
    
    {
    	"event_properties": {
    
    		 "listing": {
    
    			"delay_event_reads": true
    		}
    	}
    }

| 

  * Event display correctness

| **Configuration:**

  * `config.json`
