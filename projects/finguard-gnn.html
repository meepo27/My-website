Problem Statement

Traditional rule-based AML systems evaluate transactions in isolation. Money-mule networks deliberately fragment illicit flows across dozens of seemingly ordinary accounts — each individual transaction appears benign, but the relational structure of the network reveals the scheme.

HSBC's Asia-Pacific fraud team needed a system to reason over the full transaction graph in real time, identify coordinated mule rings, and generate explainable risk summaries for compliance analysts — all within FCA and MAS regulatory constraints.

System Architecture

Transaction Ledger (Azure SQL) → TigerGraph (GSQL ingestion) → GSQL Pattern Queries → GraphSAGE GNN (PyG) → Azure ML Endpoint → GPT-4 Narratives → Case Management Portal

Graph Store — TigerGraph & GSQL

The transaction ledger is continuously ingested into TigerGraph — a purpose-built distributed graph database chosen for its native parallel graph (NPE) execution and GSQL support. Each account becomes a vertex; fund transfers become directed edges with attributes (amount, timestamp, channel, merchant category).

GSQL pattern-matching queries pre-filter the graph before GNN scoring: a 2-hop neighbourhood query identifies accounts that share circular flow characteristics (A → B → C → A), rapid fan-out patterns, or unusually high-degree connectivity — reducing the GNN's input graph from millions of nodes to a targeted high-risk subgraph.

  • Nightly full-graph refresh from Azure SQL Data Warehouse via GSQL bulk load
  • Intraday incremental updates via Kafka → TigerGraph connector for real-time edge additions
  • GSQL queries return JSON subgraphs consumed by the PyTorch Geometric pipeline

GNN Model

A 3-layer heterogeneous GraphSAGE (PyTorch Geometric) aggregates neighbourhood information across the pre-filtered subgraphs. Node features encode account history metrics; edge features encode transaction velocity, amounts, and temporal patterns.

Training uses a weighted BCEWithLogitsLoss (positive weight ~99× due to ~1% mule prevalence). The trained model is served as a real-time Azure ML managed endpoint, scoring flagged subgraphs on demand.

LLM Risk Narrative Layer

All accounts scored above the risk threshold are enriched with a plain-English risk narrative generated by GPT-4 Turbo (Azure OpenAI). The prompt injects GNN score, subgraph features (circular flow flag, rapid-transaction count, connected-account count), and instructs the model to produce a 3–4 sentence analyst-ready summary — reducing case write-up time from ~45 minutes to ~18 minutes on average.

MLOps & Deployment

  • Model training, evaluation, and registration managed in Azure ML with full lineage tracking
  • CI/CD pipeline via Azure DevOps: PR → unit tests → integration tests → staging → production
  • Model performance tracked weekly against a held-out labelled set; drift alerts trigger retraining
  • Inference endpoint containerised with Docker, deployed on Azure Kubernetes Service (AKS)
  • All model decisions logged for Model Risk Management (MRM) audit — FCA-compliant model documentation maintained
